# docs/api/ — the interface surface

What eqlp exposes, what produces and consumes each piece, and the path to
letting plugins (written by people or agents) consume it all without
touching eqlp's internals. `commands.md` and `packs.md` are GENERATED by
`tools/gen_api_docs.py` — rerun it after changing the command surface or a
pack, commit the result.

## Architecture, one screen

```
wiki (eqlwiki.com)                 game install (user-facing files)
  │ tools/scrapers/*.py              │ log file        (/log)
  ▼                                  │ Achievements.txt
packs/*.json  ── include_str! ──┐    │ inventory dump  (/outputfile)
                                │    │ maps/*.txt      (user-editable)
                                ▼    ▼
crates: core (parse engine) ← source (tail/clock) → store (event rows)
                                     │
                              session (graph/timeline/entities)
                                     │
                        app: Ingest + feature modules (dropwatch,
                        skyquests, gearplanner, maps, …)
                                     │  *Dto structs
                        commands.rs (#[tauri::command] × 104)
                                     │  Tauri IPC (JSON)
                        ui/ (Svelte; types hand-mirrored in api.ts)
```

Nothing reads the game client's process, memory, or network — inputs are
the files the game writes for the user, plus wiki scrapes. That boundary
is load-bearing (ToS); plugins get the same rule.

## The three interface families

1. **Data packs** (`packs/*.json`) — static wiki-derived catalogs, embedded
   at compile time, each behind one `*data.rs` accessor module. Catalog:
   `packs.md`. Producers: `tools/scrapers/`.
2. **Commands** — the query surface the UI runs on; the de-facto API.
   Catalog: `commands.md`. Split there into **pure** (args + packs only)
   and **stateful** (read the live session).
3. **Game-file inputs** — the log (parsed by the rule pack `packs/eql.toml`),
   `Achievements.txt`, inventory dumps, map files. Formats documented in
   `docs/design/parsing.md` / `sources.md`.

## Decoupling audit (2026-08-29)

Clean today:
- Crate layering is real: core/source/store/session have no app dependency;
  the parser engine is reusable outside the app (the cli crate proves it).
- Every pack sits behind one accessor module; no feature module parses JSON.
- The UI touches backend state only through DTO commands — no shared types,
  no reach-ins. Feature modules read `Ingest`, never each other's internals.
- Scrapers now live in `tools/scrapers/` (imported 2026-08-29 from ~/eql).

Gaps, in priority order:
1. **82 of 104 commands take Tauri `State`/`AppHandle`** — the command layer
   is welded to the Tauri shell. Exposing endpoints means extracting each
   body into a plain function over `(&Ingest, &Config, …)` with the Tauri
   command as a thin wrapper. This is mechanical but is THE prerequisite.
2. **TS types are hand-mirrored** (`ui/src/lib/tauri/api.ts`) — every DTO
   exists twice and drifts silently. The fix is generated bindings
   (JSON Schema or TS emitted from the Rust structs); until then api.ts is
   the reference for the wire shape, the Rust struct for semantics.
3. **9 packs are bare** (no `{source, scraped, count}` envelope):
   hp_table, mana_table, invocation_classes, skill_classes, spell_classes,
   spell_flavor, spell_stacking, stance_classes, teleport_landings. They
   carry no provenance; converting them touches each loader once.
4. **items.json's producer is unversioned** — several generations of the
   v4 scraper exist outside the repo (~/eql, ~/Downloads); one needs to be
   blessed and imported like the other twelve.
5. **User-file formats are implicit** — preferences.json, profiles.json,
   the parse-history store. Fine while internal; documented the day a
   plugin wants them, not before.

## Conventions (standard going forward)

- Pack envelope: `{"source": <url>, "scraped"|"built": <ts>, "count": n,
  <payload key>: …}`. New packs conform; bare packs migrate when touched.
- DTOs: `*Dto` suffix, `#[derive(Serialize)]`, snake_case fields. Unknown
  is `null` and distinct from false/0 — "no Achievements.txt found" is not
  "not completed" (the honest-unknown rule, used throughout).
- Commands: nouns for queries (`get_*`, `list_*`, `find_*`); anything a
  plugin could ever call must not require Tauri types in its body.

## Endpoint roadmap

1. **Catalog (done)** — this directory; regenerate on change.
2. **Service layer** — extract stateful command bodies from Tauri plumbing.
   Pure functions over `(&Ingest, …)`; commands become one-line wrappers.
3. **Local endpoint** — a localhost HTTP/WS listener (opt-in, off by
   default) serving the same JSON the commands return, plus a push stream
   for parse-tick events (what the overlay already polls for). At that
   point a plugin is: any process speaking JSON to localhost.
4. **Generated schemas** — JSON Schema per DTO emitted from Rust, killing
   gap 2 and giving agent-written plugins a machine-readable contract.
