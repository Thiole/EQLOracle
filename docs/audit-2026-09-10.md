# Performance and data-model audit — 2026-09-10

Base commit: `908deb3`. Log used for every measurement: the real
`eqlog_Manipulator_rivervale.txt`, 419.8 MB, 5,250,125 lines.

**Read this first.** Line numbers drift. Every item below names a **file and a
function**. Find the function by name (`grep -n 'fn <name>' <file>`), not by
line number. If a function named here does not exist, the change was already
made — check `git log` before redoing it.

**Every cost in this document was measured, not estimated**, unless the item
says `ESTIMATED`. Do not trust a cost claim that is not in a table here; two of
the three exploratory passes that fed this audit over-stated costs by 10x
because they assumed the store holds every parsed line. It does not — see §1.

---

## 1. Ground truth: what the app actually holds

Run this yourself before changing anything. It is the only way to know whether
a change helped.

```
cargo build --release -p eqlp-app --example audit_profile
(ulimit -v 8000000; ./target/release/examples/audit_profile <path-to-log>)
```

The `ulimit` is not optional. An unbounded replay probe has OOM'd this machine
twice. A healthy full replay peaks around 375 MB.

After replaying the whole 419.8 MB log:

| quantity | value |
|---|---|
| lines parsed | 5,250,125 |
| **events kept in the store** | **753,003** |
| encounters | 7,809 |
| interned names | 13,506 |
| interned abilities | 4,645 |
| effect pings | 402,258 |
| entities with effects | 5,808 |
| zone visits | 848 |
| backfill wall time | 19.2 s (274k lines/s) |
| peak RSS | 374 MB |

**The store holds 753k events, not 5.25M.** `Ingest::route` compacts on every
zone line (`Store::compact_before`), folding closed fights' combat rows into
aggregates. Any reasoning that says "N = 2 million events" is wrong by 3x.

## 2. Already fixed in this pass

Do not redo these. Each has a regression test or a measurement.

| # | What | Before | After |
|---|---|---|---|
| F1 | Debug `effects` table browse | 371 ms | **22.6 ms** |
| F2 | Debug `timeline` table browse | 100 ms | **0.04 ms** |
| F3 | Debug `encounters` / `entities` / `chat` browse | 16.4 / 11.0 / 5.9 ms | 11.0 / 7.2 / 3.5 ms |
| F4 | `list_encounters(50)` | 0.38 ms | **0.07 ms** |
| F5 | Drop Watch silently stopped counting loot after the first zone change | broken | fixed, test added |
| F6 | Parse history re-read and re-parsed from disk twice per tick | 2 file reads/tick | 1 `metadata()` call/tick |
| F7 | Per-tick IPC fan-out | ~18 calls per tick, up to 10 Hz | coalesced to ~2.8 Hz, chat and raid gated to their module |
| F8 | `Overview` re-ran its "load once" effect on every tick | 10 Hz | once, plus on settle |
| F9 | `lastLocation` / `zoneContext` notified subscribers every tick with a fresh object | 10 Hz | only on real change |

**F1–F4, how.** `dbsearch::from_values` used to render every row of a table to
strings and sort all of them in order to show 100. It now sorts an index of
sort keys and renders rows lazily, so only the rows that survive the limit are
ever built. `effects` and `timeline` additionally got dedicated row builders
that skip `serde_json::Value` entirely, the same shape `events` already had.

**F5, the bug.** `dropwatch::loot_status` folds loot from a row *position*
(`Ingest::loot_scan_next_row`). `Store::compact_before` removes rows, so
positions move. Measured in the regression test: the store went from 41 rows to
5 across one zone line while the watermark stayed at 41, and every drop after
that point was never counted for the rest of the session. Fixed by resetting
the watermark and the fold when compaction removes anything. This is safe
because compaction only folds combat rows (`is_combat` gate in
`Store::compact_before`), so a loot row is never removed and a fresh fold gives
the identical total. Test: `crates/app/tests/dropwatch_compaction.rs`.

**F7, what changed.** `ui/src/lib/tauri/events.ts` now buffers the tick and
runs one fan-out per 350 ms window, and skips `onChatTick` unless Social is the
open module and `refreshRaidRows` unless Endgame is. Both of those modules load
on mount, so gating them cannot leave stale data. The settle path runs
everything ungated.

**Also fixed, smaller, all measured on backfill or the meter:**
`Ingest::split_instances` returned early when no charm is open, saving four
string allocations on every damage line; `Ingest::is_hidden` and
`Ingest::manual_pet_owner` return early when their maps are empty, which is the
normal case, saving a lowercased allocation on the innermost path of
`allegiance_at`; `LineCounts::by_kind` no longer allocates a key that already
exists on every matched line; `combat::live_meter_with`'s engagement fixpoint
and `combat::resolve_members` use a `HashSet` instead of a linear scan of a
growing `Vec`; `dbsearch::flag_names` renders the twelve cast, craft and
mitigation flags it was dropping as raw hex; the Debug `effects` table now
shows `source`, `skill` and `landed`, and `effects` and `timeline` expose the
entity's `Sym` beside its name so they can be joined.

## 3. Not yet fixed — ranked by measured cost × frequency

### A1. `raiding::list_raid_rows` costs 9.9 ms and runs on every tick

**Where:** `crates/app/src/raiding.rs`, `list_raid_rows`, and its helpers
`build_kill_grid`, `build_times`, `build_loot_index`.

**Now:** three separate full passes over the store, plus, for each of the six
curated raids, a scan over every zone visit matching that raid's zone, and
inside that a scan over all 7,809 encounters.

**Cost:** 9.9 ms measured, per call. It was called on every parse-tick from
`events.ts` regardless of which module was open; F7 now gates it to the Endgame
module, so the cost only lands while Raiding is on screen. It is still the most
expensive per-tick path.

**Do this:**
1. In `build_times`, replace the per-raid loop with one pass: bucket every
   encounter by `ing.zone.index_at(e.start_ms)` into a
   `HashMap<Option<usize>, Vec<&Encounter>>` once, then have each raid read its
   own buckets. This turns `raids × visits × encounters` into `encounters`.
2. Cache the finished `Vec<RaidRowDto>` on `Ingest` behind a dirty flag. Set the
   flag in `Ingest::apply` for `Action::Loot`, `Action::Xp`, and wherever an
   encounter closes. Clear it when `list_raid_rows` rebuilds.

**Verify:** add `raiding::list_raid_rows` to `audit_profile` (it is already
there) and re-run. Target is under 1 ms.

**Risk:** low for step 1, medium for step 2 — a missed invalidation shows stale
raid rows. Prefer step 1 alone if unsure.

### A2. Whole-history scopes cost 58–77 ms on the main thread

**Where:** `crates/app/src/combat.rs`, `list_side` (behind `list_allies` and
`list_enemies`) and `summarize`.

**Now:** 76.7 ms, 75.3 ms and 58.1 ms respectively when the selection covers
every fight. Per fight they are 0.01 ms and 0.00 ms. The cost is entirely
proportional to how many fights are in scope.

**Why it is slow:** the per-row loop in `list_side` allocates roughly eight
heap strings per damage row. Per row it calls `Ingest::effective_name` (returns
an owned `String`), `store.name(target).to_string()`, `allegiance_at` twice
(each one re-derives `fold_key` up to three times), and `to_lowercase()` on
both names. `combat::list_encounter_mobs` in the same file already solves this
correctly and is the pattern to copy.

**Do this:** at the top of the accumulation loop, add
`let mut side: HashMap<Sym, (bool /*enemy*/, Sym /*credited*/, Kind)>`. For each
row, look the actor and target `Sym` up in that map; only on a miss do the
`effective_name` / `allegiance_at` work and insert. Within one call `ts` moves
forward monotonically and none of these answers change inside a fight, so the
memo is safe. Resolve `Sym` back to a display string once per distinct entity
when building the DTOs, not per row.

**Also:** `PRIMARY_MELEE.contains(&ab)` in the same loop is a linear scan of 14
strings with full string comparison, per row. Build a
`OnceLock<HashSet<AbilityId>>` from the interner instead.

**Verify:** `audit_profile` prints `combat::list_allies(all fights)`. Target is
under 20 ms. The Playwright suite plus `cargo test --workspace` must stay green;
`crates/app/tests/adversarial.rs` covers the fold semantics this touches.

**Risk:** medium. This is the code that decides which side an entity is on. Do
not change any of the ownership fallbacks, only how often they are consulted.

### A3. `combat::current_encounter` scans the whole store whenever no fight is open

**Where:** `crates/app/src/combat.rs`, `current_encounter`. Called first thing
in `live_meter_with`.

**Now:** `(0..ing.store.len()).rev().find(...)`. It exits after a few rows when
a fight is open. When nothing is open — every moment you are not fighting — it
walks all 753k rows and returns `None`.

**Cost:** this is most of the measured 0.89 ms for `live_meter`, and it runs on
every tick plus a 2 s heartbeat per open widget.

**Do this:** keep `open_involving: BTreeSet<EncounterId>` on `Ingest`. Insert
where an encounter is opened and marked as involving you; remove where it is
closed or absorbed. `current_encounter` reads `.last()`.

**Verify:** `audit_profile`'s `combat::live_meter`. Target under 0.1 ms.

**Risk:** low, but the insert and remove sites must be exhaustive. Grep for
every write to `Encounter::involves_you` and every close path.

### A4. Two more reverse full-store scans with the same failure mode

**Where:** `crates/app/src/targeteffects.rs`, `target_sym`; and
`crates/app/src/combat.rs`, `encounter_for`.

**Now:** both do `(0..len).rev().find_map(...)` looking for the newest row
naming a `Sym`. Both run to completion when that entity has no rows — which is
the case whenever the tailed log is not the player's own character, or the
player has been idle.

**Cost:** `target_effects` measures 0.32 ms, and it runs on every Skill Tracker
widget tick.

**Do this:** the general fix is `last_row_for: HashMap<Sym, u32>` maintained in
`Store::push`. It must be remapped by `Store::compact_before` using the same
`new_index` table the encounter ranges already use. Both scans become an O(1)
lookup, and A3 can use it too.

**Risk:** medium — anything holding a row position must be remapped by
compaction. See A9 for another instance of the same hazard.

### A5. `Ingest::record_history` does two full-store passes per fight close, live only

**Where:** `crates/app/src/ingest.rs`, `record_history`, called from
`drain_closed`.

**Now:** builds a `Filter::default().damage().by(you).target(...)` with no
encounter set, so `query::range_of` yields `0..store.len()`, and
`query::by_ability` scans its range twice. It is gated off during backfill; the
function's own comment says the cost is known.

**Cost:** ESTIMATED at roughly 2 × 753k row visits per fight close, on the tail
worker thread, while holding the ingest mutex. Not measured because the harness
replays rather than tails. In XP-grind play a fight closes every 10–60 s.

**Do this, cheapest first:** add a `since_ms` to the filter so the scan is
bounded by `partition_point` to the last few hours of log time. The proper fix
is to fold the baseline incrementally in `commit_damage` into
`HashMap<(Sym, u8), HashMap<AbilityId, AbilityRow>>` and have `record_history`
read it.

**Verify:** this one needs a live tail, not a replay. Instrument with a timer
around `record_history` and watch a real session, or set `keep_full_history`
and replay with `mark_live` set early.

### A6. `query::by_ability` scans its range twice

**Where:** `crates/store/src/query.rs`, `by_ability`.

**Now:** two loops over the same range; the second exists to apply
`full_power`, which needs `Abilities::ceiling`.

**The claim to check first:** `Abilities::ceiling` is a session-wide high-water
mark maintained in `Store::push`, so it is already correct before the query
starts, which would make the second pass unnecessary. **Verify this before
acting** — read `Store::push` and confirm the ceiling is not derived from the
filtered rows. If it is session-wide, fold the `full_power` test into pass one.

**Cost:** doubles every caller. `summarize` makes up to six `by_ability` calls
per member fight.

**Verify:** `crates/store/tests/query.rs` must stay green, and
`audit_profile`'s `combat::summarize(all fights)` should drop.

**Risk:** medium. This changes query semantics. Write a test that compares old
and new output over the reference fixture before deleting the second pass.

### A7. `groupbuffs::group_buffs` clones a spell-file entry 12,000 times per call

**Where:** `crates/app/src/spelltimers.rs`, `entry_of`; called from
`crates/app/src/groupbuffs.rs`, `kind_of_with`.

**Now:** `file.get(&name.to_ascii_lowercase()).cloned()` — a string allocation
plus a deep clone of a struct owning a `Vec<SlotEffect>`, on every lookup. The
caller loops over all 2,010 spells once per party member plus once for innates.

**Cost:** measured at only 0.21 ms per call, so the practical impact is small.
Listed because the fix is nearly free and the allocation volume is large.

**Do this:**
1. Change `entry_of` to return `Option<&SpellFileEntry>`. Every caller only
   reads.
2. Precompute `BuffKind` per spell once into a `OnceLock<Vec<Option<BuffKind>>>`
   indexed by spell position. It depends only on the spell and the spell file,
   both fixed for the process.

**Risk:** low.

### A8. `gearplanner::recommend` scans 6,988 items per equipped slot, then sorts everything to keep 50

**Where:** `crates/app/src/gearplanner.rs`, `recommend`.

**Now:** for each equipped slot it does
`items().iter().find(|it| it.name.eq_ignore_ascii_case(name))` — a linear scan
of all 6,988 items. Then it scores candidates for 22 slots and calls
`sort_by` followed by `truncate(per_slot)`.

**Cost:** ESTIMATED. Not measured — it is on-demand from the Gear Planner tab,
not per tick.

**Do this:**
1. Build a `OnceLock<HashMap<String, &'static Item>>` keyed on the lowercased
   name for the equipped lookup. `spelldata::SPELLS_BY_NAME` is the existing
   pattern and its comment documents the same regression.
2. Replace `sort_by` + `truncate` with `select_nth_unstable_by(per_slot)` then
   sort only the kept prefix.

**Risk:** low. Item order within equal scores may change; check the planner
tests.

### A9. A store row has no stable identity, and one struct stores a raw row index

**Where:** `crates/app/src/ingest.rs`, `PendingXp`, field `row`.

**Now:** `row: u32` is a positional index into the store's columns, later
dereferenced as `self.store.enc[p.row as usize]`. `Store::compact_before`

**Cost:** no live bug today — a `p.ts == ts` guard means the stale index is not
reached in practice. This is a latent hazard of the same class as F5, which

**Do this:** either carry `(ts, EncounterId)` instead of a row index, or add the
row-index remap from A4 and apply it here too. At minimum, add a comment at the
field naming compaction as the hazard.

## 4. Data model: identity, keys, and joinable tables

### 4.1 The app names one entity seven different ways

There is no single entity identity. These key spaces coexist and none is
interchangeable with another:

| key space | how it is made | example holders |
|---|---|---|
| raw log string | as parsed | `ChatLog` keys, `Live::entities` |
| `fold_key` | first character lowercased only | `Entities::kind` / `owner` / `display` / `charms`, `GroupTracker::entries` |
| `to_lowercase()` | full fold | `charm_hints`, `ally_last_seen`, `manual_pet_owners`, `hidden_entities`, `death_enc` insert |
| `to_ascii_lowercase()` | a fourth, subtly different fold | `disposed_items`, `loot_scan_counts`, `death_enc` read |
| display name | first-observed casing, via `resolve_name` | `pet_owner` keys and values, `charmed_pets`, `seen_actors`, `behavioral_pets` |
| `Sym(u32)` | the store's interner | `store.actor` / `target`, `Encounter::target` |
| bare `u32` | a `Sym` with its type erased | `Timeline::by_entity`, `Effects::by_entity`, class detector chains |

**What this costs.** `Ingest::allegiance_at` touches five of them and
heap-allocates on every call. It is called twice per damage row by the live
meter and twice more per damage row at ingest time.

**One latent correctness bug worth fixing on its own:** `death_enc` is inserted
with `to_lowercase()` and read with `to_ascii_lowercase()`. These agree for
ASCII and diverge for anything else. Pick one. Find both sites by grepping
`death_enc`.

**Direction, not a single change:** collapse the five string key spaces onto
`Sym`. Every name in those maps is already interned in `store.names`.
`Ingest::resolve_name` allocates a fresh `String` on every call and is called
around four times per damage row. The mechanical version of this change is to
split the mutating half (`Entities::observe`) from the reading half, call the
mutation once at the head of `record_damage`, and give the read sites a
`resolve_name_ref(&self, name) -> &str`.

**Do not attempt this in one commit.** Convert one map at a time, each with the
full test suite green in between.

### 4.2 Two index spaces share one type and one column name

`classdetect.rs` declares `pub type Unit = Option<usize>` and
`pub type ZoneVisit = Unit` — the same alias for two different index spaces:
positions in `UnitTrack::spans`, and positions in `Spans` (zone visits).

- `CharmMeta::visit` is a **unit**, taken from `units.current()`.
- `petowners::PetOwner::visit` and `HiddenEntity::visit` are **zone visits**,
  taken from `zone.index_at`.

Both are `Option<usize>`. Both are rendered in the Debug tables in a column
called `visit`. They do not join.

**Do this:** make them two newtypes, `UnitId` and `VisitId`. The compiler will
find every site. No runtime behaviour changes.

### 4.3 The one piece of persisted state with a positional foreign key

`pet_owners.json` and `hidden_entities.json` key on
`(Option<usize> /*zone visit ordinal*/, name)`. That ordinal is a position in
`Spans`, which changes when the log rolls, when a replay starts from a
different point, or when a late zone line is inserted out of order.

**Consequence:** a right-click "assign to player" or "hide" can silently attach
to a different zone visit on a later run.

**Do this:** key on the visit's `start_ms`, which is already stable and already
carried in `ZoneVisitDto::start_ms`. Add a one-shot load-time upgrade that maps
existing ordinals through the current `Spans` and rewrites the file. This is
the only place in the app that needs a migration; everything else is rebuilt by
replay.

### 4.4 The Debug tables mostly cannot be joined

Two tables expose a stable id: `names.sym` and `abilities.id`. One join works
end to end: `events.enc` → `encounters.id`. `effects` and `timeline` now also
expose `entity_sym` (fixed in this pass).

Everything else renders a resolved display string and discards the id it had in
hand. **Every fix below is a pure addition to a render function.** Add columns;
never rename or reorder existing ones, because the rendered row is the contract
a custom trigger will match against later.

| table | where it is built | add |
|---|---|---|
| `events` | `dbsearch::events` | `actor_sym`, `target_sym`, `ability_id`, and the row index — without these it joins to nothing but `encounters` |
| `encounters` | `debugview::list_debug_encounters` | `target_sym`, `zone_sym`, and `zone_visit` (from `ing.zone.index_at(e.start_ms)`) so it joins `zones.index`; also restore `end_ms`, `slain`, `wiped`, `absorbed`, which exist on `Store::Encounter` and are dropped by the DTO |
| `entities` | `dbsearch::table_values`, `"entities"` arm | the `fold_key` itself — `Entities::all` has it in hand and renders only the display name |
| `instances` | same file, `"instances"` arm | `sym` |
| `party` | `debugview::game_state` | the fold key and `last_ms`, both of which `GroupTracker::current_members` already returns and the DTO discards |
| `chat`, `pms` | `dbsearch::table_values` | resolve `who` through `Entities::display_name` so it joins `entities` and `party` |
| `spellbook` vs `spell_ranks` / `spell_perf` | `progression::spellbook` | `spellbook` keys on the full name with its rank suffix; the other two key on the rank-stripped base. Add a `base` column to `spellbook` |
| `drops` vs `zone_drops` | `Ingest`, the `observed_drops` and `observed_zone_drops` writers | `drops` stores the mob lowercased and the item in original casing; `zone_drops` stores the item lowercased. They cannot be joined on `item`. Pick one casing for both |

### 4.5 State stored twice that can drift

1. **`Encounter::zone` vs `zone_visit_of`.** The store caches a zone `Sym` on
   the encounter at open time; `combat::zone_visit_of` re-derives it from
   `Spans::index_at`. `Spans::enter` handles out-of-order insertion, so a late
   zone line shifts `index_at` for every later fight while the cached `Sym`
   stays frozen. `list_debug_encounters` reads the cache; the visit filter in
   `list_encounters` reads the derivation. **Verify this divergence with a test
   before changing anything** — construct a replay with an out-of-order zone
   line and compare the two answers.
2. **`entities_by_enc`** duplicates what `Live::entities` and `Closed::entities`
   already hold, and is written by cloning a `Vec<String>` on every damage edge.
   Store the encounter id and read through the graph instead.
3. **`Timeline::all` and `Timeline::by_entity`** store every transition twice.
   Both are written in one function so they cannot drift today.
4. **`ExaltationProcs::counts` and `first_seen_ms`** are two maps on one key.
   Merge into one map with a two-field value; `all()` already re-joins them.
5. **`Entities`' four maps on one key** (`kind`, `owner`, `display`, `charms`)
   mean up to three key allocations per write. One `HashMap<String, EntityRow>`
   removes them.

### 4.6 Missing indexes

**There is no index on `EventKind`.** Every consumer of a non-combat kind does a
full `0..store.len()` scan with a `continue`:

| caller | looking for |
|---|---|
| `craftlog::craft_log` | `Craft` |
| `craftlog::recent_crafts` | `Craft` |
| `skyquests::build_item_loot_index` | `Loot` |
| `monsters::xp_credited_encounters` | `Xp` |
| `monsters::item_loot_history` | `Loot` |

At 753k rows each of these is cheap in isolation (`craft_log` measures 0.29 ms).
Only build the index if a measurement says one of these is hot. **Do not build
it speculatively** — it must be remapped by `Store::compact_before`, which is
exactly the hazard that produced F5 and A9.

"All events for entity X" also has no index; `query::range_of` narrows only when
the filter carries an encounter. `Effects::recent` and `Timeline::state_at` are
the two lookups that *are* indexed, and they are the model to copy.

## 5. Frontend

### 5.1 Inactive tab panels mount and run

**Confirmed** by reading `node_modules/bits-ui/dist/bits/tabs/components/tabs-content.svelte`:
it renders its children unconditionally and hides the inactive panel with an
attribute. There is no `{#if active}`.

**Consequence:** every sub-panel of Character, Debug, Endgame and Social mounts
at once, and their `onMount` and `$effect` blocks run while the user is on a
sibling tab. Entering Character fires `SkillData`'s fetches even if you never
open that tab. Entering Endgame registers three separate `parse-tick` listeners.

**Do this:** wrap the expensive panels in `{#if activeTab === '<name>'}` inside
their `Tabs.Content`, or move their loads behind an explicit "mounted and
visible" guard. Start with `SkillData` and `ParsedPanel`.

### 5.2 Unbounded chat, fetched whole

`Ingest`'s `ChatLog` is a `Vec<ChatMessage>` per channel with no cap; `push`
never truncates. `chat::guild_chat` and its two siblings clone the entire vector
into DTOs. `ChannelChat.svelte` then copies and reverses the whole array in a
`$derived.by` and renders every message.

F7 gated this to the Social module, which removes the per-tick cost when you are
elsewhere. The size problem remains: a long session's guild channel is tens of
thousands of messages.

**Do this:** add a `limit` or `since_ms` parameter to the three chat commands and
request only the tail, or cap the backend vectors to a rolling window. Then
virtualize the message list.

### 5.3 Maps runs a 60 fps loop and a full-map scan

- `MapViewer.svelte`'s `tick()` calls `requestAnimationFrame` unconditionally, so
  a static wireframe renders 60 frames a second whenever Maps is open. Render on
  `controls.change`, while a pan is active, and on resize instead.
- `Maps.svelte`'s `nearestWall` derived scans every line segment of the current
  map. F9 stops it recomputing when the player has not moved; it still costs a
  full scan on every real `/loc`.

### 5.4 `GameData` sorts all five catalogs on every keystroke

`GameData.svelte` has five `$derived` filter-and-sort blocks. They would be lazy,
but `totalForTab` reads all five `.length` and is rendered unconditionally, which
forces all five. That is roughly 15,800 elements filtered and sorted per
keystroke, four-fifths of it discarded.

**Do this:** make `totalForTab` a `switch` on the active tab. Sort each catalog
once at load — they are static.

### 5.5 13 MB of catalogs loaded into the webview at launch

`App.svelte` calls `loadGameDataModule()` on mount, which fetches zones, NPCs,
spells, spell effects, AA, mob aliases and stacking groups. `packs/npcs.json`
alone is 10.7 MB.

**Do this:** the only thing needed at launch is name-to-existence resolution for
`GdLink`. Ship a `Set<string>` of names per kind and lazy-load the full catalogs
when Game Data actually mounts.

**Also:** `list_zones` is fetched three separate times into three separate
copies — `stores/gamedata.ts`, `stores/maps.ts`, and a third directly in
`Maps.svelte`. Have `Maps.svelte` read the store.

**Also:** `loadCharacterModule` has no memoization guard, unlike
`loadGameDataModule`. It fires ten IPC calls on every navigation to Overview,
Character or Game Data. Add the same `loading` promise guard with an explicit
`reload()` for the settle path.

### 5.6 Responsive layout

**A test-harness gap to fix first.** `App.svelte` puts `overflow-hidden` on the
app root and `overflow-y-auto` on `<main>`. CSS computes `overflow-x` to `auto`
in that case, so horizontal overflow scrolls *inside* `<main>` and never reaches
the document. `tests/render/responsive.spec.ts` only measures
`document.documentElement.scrollWidth`, so **it cannot see any of the overflow
below.** Add an assertion on `main.scrollWidth > main.clientWidth`.

**Zoom shrinks the viewport.** The Display zoom setting goes to 200%. At 125% a
760 px window is a 608 px CSS viewport; at 200% it is 380 px. Read every
breakpoint below against those numbers, not against the window size.

**Unguarded `grid-cols-2`** — each of these gives about 288 px per column at a
760 px window, and about 224 px at 125% zoom:

- `shell/Overview.svelte` — the landing page, worst impact. Its Session card
  header is `flex items-center justify-between` with no `flex-wrap`, and the
  buttons are `shrink-0 whitespace-nowrap`, so the row cannot compress. Needs
  about 420 px and gets 288.
- `character/CharacterSheet.svelte`
- `settings/SpellLinePriority.svelte` — also has a `w-72` search input that alone
  exceeds the column
- `endgame/Raiding.svelte`
- `overlay/OverlaySettings.svelte`
- `tradeskill/Tradeskill.svelte`
- `character/Inventory.svelte`

**Do this:** `grid-cols-1 min-[900px]:grid-cols-2`, and add `flex-wrap gap-2` to
the Overview session header. `combat/Combat.svelte` is the reference — it uses
`min-[900px]:` with a documented reason.

**Maps is unusable at the minimum window.** `Maps.svelte` has `min-h-[560px]` on
the outer container inside a `<main>` that is 444 px tall at a 480 px window,
forcing 116 px of overflow before its two `min-h-[480px]` children. Width leaves
308 px for the 3D viewer after the sidebar and a `w-64` NPC panel. Replace the
minimum heights with `min-h-0` and let it fill, and collapse the NPC panel below
900 px the way Combat collapses the fight tree.

**Social panes are fixed at `h-[520px]`** in `ChannelChat.svelte` and
`PmList.svelte`, taller than the 444 px available at the minimum window, and
wasted empty space at every larger one. Use `h-full min-h-0` inside a flex
column.

**`sm:` keys off the window, not the pane.** `SpellbookBuilder.svelte` uses
`grid-cols-4 sm:grid-cols-7`, but the pane it lives in is about 576 px at a
760 px window, so seven columns get 76 px each. `endgame/SkyClassUnlocks.svelte`
has a comment acknowledging the same problem. Use container queries — Tailwind 4
has them built in — or `min-[900px]:` measured from the pane.

**Fixed-width toasts** (`UpdateBanner`, `DeathRecapBanner`, `DropWatchLootBanner`,
all `w-[380px]`) fit down to 125% zoom and overflow at 200%. Use
`w-[min(380px,calc(100vw-2rem))]` if 175–200% zoom is meant to be supported.

## 7. The one thing that cannot be measured here

122 of the 132 Tauri commands are declared `pub fn`, not `pub async fn`. On
Windows a synchronous command runs on the window's own thread, which is the same
thread that has to answer a drag request. `commands::search_db` is already async
and its comment gives the reason.

This machine is Linux. **The Windows behaviour in this section is reasoned, not
observed.** Before converting commands wholesale, get one Windows user to
confirm that the window is draggable during heavy activity after the fan-out
coalescing in F7. If it is still not, convert the per-tick commands in the table
in §1 to `pub async fn` with the body inside `tauri::async_runtime::spawn_blocking`,
highest measured cost first.
